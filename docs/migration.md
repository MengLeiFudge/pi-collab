# 数据库迁移

全新数据库直接使用 schema 3。已有 schema 1/2 数据库需要显式迁移，普通打开不会自动升级。

## 升级

1. 协调所有参与会话停止写入，确认在途命令结束，并释放全部 active/release-pending assignment。
2. 准备新版本插件和 CLI，使用新版本执行：

   ```sh
   node dist/cli.js maintain migrate --json '{}'
   ```

3. 确认返回 `ok:true`、`schema_version:3` 和备份路径，再将所有参与会话切换到新版本。

迁移先取得 SQLite 写锁，检查没有维护操作和未释放范围，再设置业务入口遵守的维护门禁。备份写入 collab 数据目录的 `migration-backups/schema-<原版本>-<UUID>.sqlite3`，并清除备份中的维护标记。备份失败不升级；结构、协议触发器和 user_version 在同一事务中提交。迁移备份不参与普通七份备份轮换。

数据库身份、世代、房间内容与历史成员保持原样。迁移为当前持有者建立会话归属并更新成员显示名；同一会话若有多个旧模型槽位，仅保留最近更新槽位的持有权。已离开且没有会话归属的旧成员保留为历史记录，新会话独立加入。旧版本会被 schema/协议检查拒绝写入。

## 中断与回退

迁移进程若在设置门禁后中断且尚未升级，使用对应旧版本的 `maintain recover`，核实原 PID 已退出后解锁，再重试迁移。

迁移前备份保留原 schema，不由 schema 3 的普通 restore 接受。完整回退需停止所有 Pi、CLI 和桥接进程，归档当前整个 collab 数据目录，在原路径建立空目录，仅复制所选迁移备份并命名为 `collab.sqlite3`，再使用支持原 schema 的插件版本。不要把旧 WAL/SHM 复制到新目录。

迁移后产生的数据保留在归档中，不会出现在回退库内；回退是全库切换，不做跨 schema 合并。
